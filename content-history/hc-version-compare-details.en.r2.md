## Before you start

- Open Version history for a Dosya file in the current released client.
- Confirm the active account and workspace, then identify two known version rows.
- Use a small non-confidential test item and record its current state before changing it.
- Keep passwords, API keys, recovery keys, private links, personal data, and confidential file contents out of screenshots and support messages.

## Steps: compare entries in file version history

1. Open Version history for a Dosya file and confirm the active account and workspace.
2. Locate two known version rows and verify its name or identifying details.
3. Compare timestamps, sizes, authors, and available preview or download details before choosing one.
4. Read the displayed warning, permission, progress, or confirmation state before leaving the screen.
5. Confirm that the intended revision is identified without changing the current file.
6. Refresh, fetch, or reopen the relevant view once to verify the result persisted.

## Verify the result

After completing the steps, check the expected result: The intended revision is identified without changing the current file. Do not rely only on a success toast or submitted request. ## Troubleshooting

**The expected control is missing.** Return to Version history for a Dosya file, confirm the active workspace, and check that your role and client version support the action.

**The operation is rejected or stalls.** Read the exact message and check permissions, locks, storage, network state, source availability, and any third-party authorization before retrying.

**The result is still unclear.** Repeat with one small test item, then contact support with the time, client version, workspace, and a nonsecret error, delivery, or request identifier.
