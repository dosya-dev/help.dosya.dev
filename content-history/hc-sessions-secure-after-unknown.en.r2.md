This guide covers **Secure your account after an unknown session** in Dosya. The main action is to revoke sessions, reset the password, verify two-factor authentication, and review security notifications; the decisive check is whether old sessions are invalidated and stronger sign-in controls are active.

Keep the signed-in account, security state, plan, billing period, and saved preference in view while you work. Use step 2 to identify the exact target, then record its current state so a refresh, reconnect, or return to the page gives you a reliable comparison.

## Before you start

- Open Profile > Security and Sessions in the current released client.
- Confirm the active account and workspace, then identify unrecognized active or recent session.
- Use a small non-confidential test item and record its current state before changing it.
- Keep passwords, API keys, recovery keys, private links, and personal data out of screenshots and support messages.

## Steps: secure your account after an unknown session

1. Open Profile > Security and Sessions and confirm the active account and workspace.
2. Locate unrecognized active or recent session and verify its name or identifying details.
3. Revoke sessions, reset the password, verify two-factor authentication, and review security notifications.
4. Read the displayed warning, permission, progress, or confirmation state before leaving the screen.
5. Confirm that old sessions are invalidated and stronger sign-in controls are active.
6. Refresh or reopen the relevant view once to verify the result persisted.

## Verify the result

After completing the steps, check the expected result: Old sessions are invalidated and stronger sign-in controls are active. Do not rely only on a success toast or submitted request. Refresh or reopen the relevant view and compare the visible account, workspace, path, status, count, or permission with the state you recorded before the task.

Reopen the relevant account page and confirm the displayed value belongs to the intended account. If the result differs from what you expected, stop before repeating the action. Capture the time and nonsecret status, then check session, verification, billing, or policy requirements before trying again.

## Expected result

The controlled workflow completes and old sessions are invalidated and stronger sign-in controls are active. The result remains visible after a refresh, reconnect, or return to the relevant screen.

## Limits and important details

- Available controls depend on the current client version, account plan, workspace role, and policy.
- Processing, indexing, background transfer, or third-party authorization can delay a visible result.
- For destructive, access-changing, or automation actions, validate with disposable data before applying the workflow to important files.

## Practical checks

- Confirm you are working in the intended account and workspace before selecting the target.
- Re-read the exact target name, folder path, member, endpoint, or provider shown by the interface.
- Complete one controlled example first when the action can affect access, create copies, move data, or start a transfer.
- Verify the final state after a refresh; keep only nonsecret timestamps, statuses, and request identifiers for support.

## Troubleshooting

**The expected control is missing.** Return to Profile > Security and Sessions, confirm the active workspace, and check that your role and client version support the action.

**The operation is rejected or stalls.** Read the exact message and check permissions, locks, storage, network state, source availability, and any third-party authorization before retrying.

**The result is still unclear.** Repeat with one small test item, then contact support with the time, client version, workspace, and a nonsecret error or request identifier.

## Frequently asked questions

### What should I check before repeating this task?

Return to the first step and confirm the active account, workspace, and target. Then compare the current state with the result described above. Repeating the action without that comparison can create duplicates, overwrite the wrong setting, or make the original error harder to diagnose.

### What details should I include when asking for help?

Include the action time, client or browser version, active workspace, expected result, visible status, and any nonsecret error or request identifier. Never include passwords, API keys, recovery codes, private sharing links, payment details, or confidential file contents.
